# 自己再生する群ロボット — エピジェネティック・トラッキングによる形状形成と再生のシミュレータ

司令塔を持たず、近くの仲間との通信だけで全体の形（秩序）をつくり、切られても作り直す群ロボットの論文を、ブラウザで動かして理解するためのシミュレータです。

## 参照した論文

- Rahul Shivnarayan Mishra, Tushar Semwal, Shivashankar B. Nair,
  **"A Distributed Epigenetic Shape Formation and Regeneration Algorithm for a Swarm of Robots"**,
  GECCO '18 Companion (Genetic and Evolutionary Computation Conference Companion), Kyoto, 2018.
  DOI: [10.1145/3205651.3208300](https://doi.org/10.1145/3205651.3208300) / arXiv: [1810.11935](https://arxiv.org/abs/1810.11935)
- PDF: [`paper/Mishra2018_EpigeneticShapeFormation_arXiv1810.11935.pdf`](paper/Mishra2018_EpigeneticShapeFormation_arXiv1810.11935.pdf)（arXiv 版。著作権は著者と ACM にあります）

### 選んだ理由（テーマとの対応）

| テーマ | 論文の内容 |
| --- | --- |
| 司令塔を持たない | 全ロボットが同じプログラムと同じ「遺伝子」を持ち、中央制御なしで動く |
| 周囲の個体とのみ通信 | Kilobot の赤外線通信（数 cm）だけで、近傍の座標・状態・TS を交換する |
| 全体での秩序形成 | 二値画像で与えた形（T・ダンベル・ヒトデ）を三角格子の上に組み上げる |
| 自己組織化・非同期分散 | 8 状態の有限オートマトンを各個体が非同期に実行。切断されると、各断片がリーダー選出、人口調査、縮小形状の生成を行い、自分たちで再生する |

## アプリの使い方

`index.html` をブラウザ（Chrome / Edge / Safari / Firefox）で開くだけで動きます。外部ライブラリは使っていません。フォントは Google Fonts から読み込みますが、オフラインでも代替フォントで動きます。

| 操作 | 内容 |
| --- | --- |
| 再生 / 一時停止、1 歩、最初から | シミュレーションの操作（スペースキーでも一時停止） |
| 形状 | T（論文 図1）／ダンベル（図8）／ヒトデ（図9）／自作（遺伝子パネルのビットマップをクリックして編集） |
| 速度・メッセージ損失 | 1 フレームあたりの tick 数と、通信が失われる確率（論文の実験値は 0.2） |
| 線を引いて切る／縦に切る／横に切る | 群れを切断し、再生（Danger → リーダー選出 → 外周の一周による人口調査 → 縮小形状 → 再形成）を観察する |
| ロボットをクリック | そのロボットの記憶（状態、Tag、TS、NN、近傍数、聞こえている近傍の表）と通信範囲を表示する |
| 補助ルール | 論文にない補助ルールをオン・オフする（下記） |

右側のパネルには、状態ごとの台数、形ごとの完成度、8 状態の遷移図、遺伝子の表 (X, Y, F, NN)、出来事のログが出ます。直近に起きた遷移は遷移図で光ります。

## 実装の要点

- **エージェント**: 各ロボットは毎 tick（0.2 秒）自分の公開情報を放送します。通信範囲（85 mm）内の仲間に、確率 1−損失率 で届きます。全員が同じ `think()` をランダムな順番で非同期に実行します。判断に使うのは自分の記憶と受け取ったメッセージだけです。
- **論文どおりの部分**: 二値画像 → 斜交座標系 → 遺伝子 (Tag, Flag, NN) の計算。Queued / Search / Inactive / Active / Quasi / Stable / Danger / Leader の遷移。TS 勾配と Quasi への退避。最小 ID による待機列からの出発。近傍数の減少による損傷検出。最小 ID のリーダー選出。外周の一周による人口調査。境界の 1 を削る縮小画像。新シードからの再形成。
- **物理量**: Kilobot の直径 33 mm、格子間隔 40 mm、速度 10 mm/s。

### 論文に書かれていない部分の補い方（補助ルール）

論文は短い Companion 論文で、移動制御などの詳細が書かれていません。そのため次のように補いました（アプリ内の解説にも同じ一覧があります）。

1. 近傍の相対位置（距離と方位）が測れるものとした（実機の Kilobot は距離のみ）。
2. 入る格子点を決めたら、近傍の座標から推定した格子上の短い経路（最大 5 歩）で移動する。
3. 各ロボットは自分の 6 近傍の占有状況を 6 ビットで発信する。
4. 穴防止: 空きセルを閉じ込める位置には入らない。周り 4 方向以上が埋まったくぼみは、TS 最小の規則の例外として先に埋める。
5. 遷移の聞き逃しの救済: Inactive が、同じ形の Stable の隣で一定時間待っても Active が来なければ Active になる。
6. 待機列は外側の個体から出発する（その中では最小 ID の規則を守る）。
7. 縮小形状は、残った個体と最も重なる位置・向き（60° 刻み）に置く。縮小版を作れない場合は、残った形をそのまま新しい形とする。
8. リーダー選出と新形状の受け渡しは、接している個体どうしで中継する（切断で分かれた塊ごとに再生するため）。
9. 迷子の探索個体は、最後に聞こえた仲間の方へ戻る。長く仲間が聞こえなければ、近くの別の群れに加わる。
10. 切断では、線の片側を通信範囲外まで引き離す（線上の個体は失わない）。

### 動作確認

ヘッドレス（Node.js）で同じエンジンを動かして確認しました。

- **形成**: T（39 台）・ダンベル（52 台）・ヒトデ（58 台）。それぞれ乱数 6 通り、損失率 0.2 で、全台が Stable になって完成した。
- **再生**: T を縦と横に切った場合、両方の断片が縮小版を作り直して完成した。ダンベルとヒトデを横に切った場合も同じ。
- **再生の失敗例**: ダンベルとヒトデを縦に切ると、断片が細かく分かれ、1〜数台が残ることがある（論文 図6 の「誤った状態に残る個体」に近い）。
